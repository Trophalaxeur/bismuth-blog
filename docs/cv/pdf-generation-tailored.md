# Tailored CV PDF Generation

## What this is

Unlike the 6 static, committed PDFs described in [pdf-generation.md](./pdf-generation.md), a **tailored** CV — adapted to a specific job offer or a custom prompt, generated on demand from the `bromine-cv-extension` Firefox extension — is rendered by a separate backend (`Trophalaxeur/bromine-backend`), against `astro dev`, not a full `astro build`. This repo only provides the plumbing: a dev-only content source and a dev-only route. The generation, session/draft handling, and PDF rendering itself all live in `bromine-backend`.

## The flow

1. `bromine-backend` receives a request (job offer text, or a free-form prompt) from the extension.
2. It loads the Josiane editorial skill and the current CV source from a `carbon-notes` checkout, calls an LLM, and writes the tailored result to `carbon-notes/cv/tailored/<slug>/{fr,en}/` — same file layout and frontmatter schema as `cv/{fr,en}/`, prefix included (see [content-pipeline.md § TAILORED_CV_SLUG](../content-pipeline.md#sub-selector--tailored_cv_slug)).
3. It spawns `npx astro dev` inside a `bismuth-blog` checkout with `TAILORED_CV_SLUG=<slug>` and `LOCAL_CARBON_NOTES=<path to that carbon-notes checkout>` set.
4. Playwright navigates to `http://localhost:4321/cv/tailored/<slug>/print?variant=<short|detailed>` (or `/cv/tailored/<slug>/career-channel` for that variant) and calls `page.pdf()` — same font-swap and `printBackground` logic as the canonical `generate-cv-pdf.ts` script, so the output is visually identical to the real CV.
5. The dev server is torn down; the PDF is returned to the extension. Requests are serialized (one render at a time) — this is a low-traffic, personal tool, not a service built for concurrency.

## Why `astro dev`, not `astro build`

The canonical `cv:pdf` script builds the whole site first (`astro check && astro build`) because it produces static files meant to be committed and served indefinitely. A tailored CV is the opposite: one-off, generated on demand, needed fast. `astro dev` skips the build step entirely — the tradeoff is that **all** of bismuth-blog's content loaders still run on startup (articles, docs, not just the CV — see the content-pipeline doc's cache warning), so the first render against a cold checkout is slow. Keep the Astro Content Layer cache (`.astro/`) around between renders to avoid re-paying that cost.

## Why this repo doesn't do more than plumbing

The route (`src/pages/cv/tailored/[slug]/print.astro`) and the content source (`content.config.ts`'s `TAILORED_CV_SLUG`) are the only bismuth-blog-side pieces. Everything else — the LLM call, the session/draft lifecycle (a generated CV is editable until explicitly committed), the commit into carbon-notes for traceability — is `bromine-backend`'s responsibility, not this repo's. This keeps the production build of bismuth-blog free of any AI/LLM dependency: `TAILORED_CV_SLUG` is read behind `import.meta.env.DEV`, so none of this can activate in a real deploy (see [content-pipeline.md](../content-pipeline.md) and `middleware.ts` for the layered proof of that).
